# End-to-End Encrypted Direct Messaging System Design

## Overview

This document outlines the design for implementing end-to-end encryption (E2E) for HashPost's direct messaging system. The system will ensure that message contents are only readable by the sender and recipient, even if the database or server is compromised.

## Current State Analysis

### Existing Infrastructure
- ✅ **Direct messaging database schema** - `direct_messages` table with basic message storage
- ✅ **Message handlers** - API endpoints for sending/receiving messages
- ✅ **User blocking system** - Prevents unwanted messages
- ✅ **Pseudonym system** - Users interact through pseudonymous identities
- ✅ **IBE system** - Identity-Based Encryption for pseudonym generation and correlation

### Current Limitations
- ❌ **No message encryption** - Messages stored in plain text
- ❌ **Server can read all messages** - Database administrators have full access
- ❌ **No privacy guarantees** - Message contents exposed to platform operators

### Key Insights from Current System
1. **Pseudonyms already have cryptographic keys** - The IBE system generates pseudonym IDs using cryptographic operations
2. **Role keys exist** - Users have role-based keys for authentication and correlation
3. **Identity mappings are encrypted** - Real identities are already encrypted using IBE
4. **No migration needed** - Direct messaging is not currently exposed to users

## Design Goals

### Primary Objectives
1. **True end-to-end encryption** - Only sender and recipient can read messages
2. **Server-side key storage** - Keys encrypted with user passwords and stored on server
3. **Automatic key distribution** - Keys sent to clients upon login
4. **Forward secrecy** - Compromised keys don't expose historical messages
5. **Key verification** - Users can verify they're talking to the right person

### Secondary Objectives
1. **Performance** - Minimal encryption overhead
2. **Usability** - Transparent to users
3. **Compatibility** - Works with existing pseudonym system
4. **Auditability** - Server can verify message authenticity without reading content

## Cryptographic Architecture

### Key Hierarchy

```
User Password (derived from login)
├── Master Encryption Key (derived from password)
    ├── Message Encryption Keys (AES-256)
    ├── Conversation Keys (AES-256, shared between users)
    └── Signature Keys (Ed25519, for message authenticity)
```

### IBE Domain Integration

The messaging system integrates with HashPost's existing IBE (Identity-Based Encryption) system through role keys. Each user's messaging capabilities are controlled by role keys with specific scopes and domains.

#### Role Key Structure for Messaging
```go
// Messaging role keys use the existing role key system
{
    role: "user",
    scope: "messaging",           // New scope for messaging operations
    capabilities: [
        "send_direct_messages",
        "receive_direct_messages", 
        "manage_conversation_keys"
    ],
    subforum_id: NULL,            // Global scope for messaging
    key_data: BYTEA               // Encrypted IBE key for messaging domain
}
```

#### IBE Domain Selection for Messaging
For messaging operations, we need a **new domain** specifically for user-to-user communication:

```go
const (
    DOMAIN_USER_PSEUDONYMS   = "user_pseudonyms_v1"      // Pseudonym generation
    DOMAIN_USER_CORRELATION  = "user_self_correlation_v1" // User self-correlation (NOT messaging)
    DOMAIN_USER_MESSAGING    = "user_messaging_v1"        // User-to-user messaging (NEW)
    DOMAIN_MOD_CORRELATION   = "moderator_correlation_v1" // Moderation operations
    DOMAIN_ADMIN_CORRELATION = "admin_correlation_v1"     // Administrative operations
    DOMAIN_LEGAL_CORRELATION = "legal_correlation_v1"     // Legal compliance
)
```

**Why a Separate Messaging Domain:**
- **Messaging is fundamentally different** - it's about secure communication between users
- **Security isolation** - compromise of messaging keys doesn't affect other domains

### Key Types

#### 1. **Messaging Role Key (Master Key)**
- **Purpose**: Master key for all messaging operations, encrypted with user password
- **Source**: Generated by IBE system using `DOMAIN_USER_MESSAGING`
- **Storage**: Encrypted with password-derived key, stored in database
- **Usage**: Decrypts all other messaging keys upon login
- **Rotation**: Can be rotated when user is present (requires password)

#### 2. **Message Encryption Keys**
- **Purpose**: Encrypt individual message contents
- **Algorithm**: AES-256-GCM
- **Storage**: Encrypted with role key, stored in database
- **Rotation**: New key generated every 100 messages or 30 days
- **Backward Compatibility**: New role keys can decrypt old message keys

#### 3. **Conversation Keys**
- **Purpose**: Shared encryption key between two users for forward secrecy
- **Algorithm**: AES-256-GCM
- **Storage**: Encrypted with both users' role keys, stored in database
- **Rotation**: New key generated frequently (every 50 messages or 7 days)
- **Forward Secrecy**: Old conversation keys are discarded, new role keys cannot decrypt old conversation keys

#### 4. **Signature Keys**
- **Purpose**: Verify message authenticity and sender identity
- **Algorithm**: Ed25519
- **Storage**: Encrypted with role key, stored in database
- **Rotation**: Can be rotated independently of encryption keys

### Key Generation and Storage

#### Key Generation Process
```
1. User logs in → Password verified
2. Password-derived key decrypts encrypted role key from database
3. Role key becomes master key for messaging operations
4. Role key decrypts all other messaging keys (message keys, conversation keys, signatures)
5. New keys generated and encrypted with role key as needed
6. Encrypted keys stored in database for next login
```

#### Messaging Role Key Creation
Messaging role keys are created using the existing IBE system with the `DOMAIN_USER_MESSAGING` domain:

```go
// When a user first accesses messaging functionality
func createMessagingRoleKey(ctx context.Context, userID int64, pseudonymID string) error {
    // 1. Generate IBE key for messaging domain
    ibeKey := ibeSystem.GenerateCorrelationKey(
        "user",                    // role
        "messaging",              // scope  
        ibe.DOMAIN_USER_MESSAGING, // domain
        time.Hour * 24 * 365,     // 1 year expiration
    )
    
    // 2. Create role key entry
    roleKey := &models.RoleKey{
        RoleName: "user",
        Scope: "messaging",
        KeyData: ibeKey,
        Capabilities: []string{
            "send_direct_messages",
            "receive_direct_messages",
            "manage_conversation_keys",
        },
        PseudonymID: pseudonymID,
        SubforumID: nil, // Global scope
        ExpiresAt: time.Now().AddDate(1, 0, 0),
    }
    
    // 3. Store in role_keys table
    return roleKeyDAO.CreateRoleKey(ctx, roleKey)
}
```

**Key Management Flow:**
1. **User Registration**: Basic user role keys created (authentication, self_correlation)
2. **First Message Access**: Messaging role key created with `DOMAIN_USER_MESSAGING`
3. **Key Rotation**: Messaging keys rotated annually or on compromise
4. **Capability Updates**: New messaging capabilities added to existing keys

**Security Model:**
- **Backward Compatibility**: New role keys can decrypt old message keys and signatures
- **Forward Secrecy**: Old conversation keys are discarded, providing forward secrecy
- **Key Compromise**: Compromise of current role key exposes current message keys but not old conversation keys
- **Password Change**: Requires re-encryption of role key with new password-derived key

**Domain Selection Logic:**
The IBE system automatically selects the appropriate domain based on role and scope:
- **Role**: `"user"` + **Scope**: `"messaging"` → **Domain**: `DOMAIN_USER_MESSAGING`
- **Role**: `"user"` + **Scope**: `"self_correlation"` → **Domain**: `DOMAIN_USER_CORRELATION`
- **Role**: `"moderator"` + **Scope**: `"correlation"` → **Domain**: `DOMAIN_MOD_CORRELATION`

**Benefits of Upsert Behavior:**
1. **Non-Disruptive**: Existing domain keys are preserved during generation
2. **Incremental**: Can add new domains without affecting running systems
3. **Safe**: No risk of accidentally overwriting production keys
4. **Flexible**: Supports both initial setup and domain additions
5. **Auditable**: Clear logging of which keys are preserved vs. generated

#### Key Storage Schema
```sql
-- User encryption keys table
CREATE TABLE user_encryption_keys (
    user_id BIGINT PRIMARY KEY,
    encrypted_master_key BYTEA NOT NULL, -- Encrypted with password-derived key
    encrypted_message_keys BYTEA NOT NULL, -- JSON array of encrypted AES keys
    encrypted_signature_key BYTEA NOT NULL, -- Encrypted Ed25519 private key
    public_signature_key BYTEA NOT NULL, -- Ed25519 public key (unencrypted)
    key_fingerprint VARCHAR(64) NOT NULL, -- SHA-256 hash of public key
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    last_rotated TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    
    FOREIGN KEY (user_id) REFERENCES users(user_id) ON DELETE CASCADE
);

-- Conversation encryption keys table
CREATE TABLE conversation_keys (
    conversation_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    participant1_user_id BIGINT NOT NULL,
    participant2_user_id BIGINT NOT NULL,
    encrypted_shared_key BYTEA NOT NULL, -- AES-256 key encrypted with both users' public keys
    key_fingerprint VARCHAR(64) NOT NULL, -- Hash of the shared key
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    expires_at TIMESTAMP WITH TIME ZONE, -- For forward secrecy
    is_active BOOLEAN DEFAULT TRUE,
    
    -- Ensure consistent ordering of participants
    CONSTRAINT ordered_participants CHECK (
        participant1_user_id < participant2_user_id
    ),
    UNIQUE (participant1_user_id, participant2_user_id),
    
    FOREIGN KEY (participant1_user_id) REFERENCES users(user_id) ON DELETE CASCADE,
    FOREIGN KEY (participant2_user_id) REFERENCES users(user_id) ON DELETE CASCADE
);

-- Encrypted messages table
CREATE TABLE encrypted_messages (
    message_id BIGINT PRIMARY KEY,
    conversation_id UUID NOT NULL,
    encrypted_content BYTEA NOT NULL, -- AES-256 encrypted message content
    content_hash VARCHAR(64) NOT NULL, -- SHA-256 hash of original content
    iv BYTEA NOT NULL, -- Initialization vector for AES encryption
    signature BYTEA NOT NULL, -- Ed25519 signature for message authenticity
    key_version INTEGER NOT NULL DEFAULT 1, -- Version of encryption key used
    
    FOREIGN KEY (message_id) REFERENCES direct_messages(message_id) ON DELETE CASCADE,
    FOREIGN KEY (conversation_id) REFERENCES conversation_keys(conversation_id) ON DELETE CASCADE
);

-- Note: Messaging role keys will be created automatically in the existing role_keys table
-- using the existing IBE system with DOMAIN_USER_CORRELATION domain.
-- No additional tables needed for role key management - the system leverages
-- the existing unified permission infrastructure.
```

## Message Flow

### 1. **Permission Verification (Before Key Exchange)**
```
User A wants to message User B:
1. A's messaging capabilities verified via role key system
2. System checks if A has "send_direct_messages" capability
3. System checks if B allows direct messages (user preference)
4. System checks if A is blocked by B
5. If all checks pass, proceed to key exchange
```

### 2. **Key Exchange (First Message)**
```
User A wants to message User B:
1. A requests B's public signature key
2. A generates random AES-256 conversation key
3. A encrypts conversation key with B's public key
4. A stores encrypted conversation key in database
5. A can now send encrypted messages to B
```

### 3. **Permission Integration with Existing System**
The messaging system integrates seamlessly with HashPost's unified permission system:

```go
// Example: Checking messaging permissions in a handler

    }
    
    // 3. Proceed with encrypted message creation
    // ... rest of implementation
}
```

### 2. **Message Encryption**
```
User A sends message to User B:
1. A retrieves conversation key from database
2. A generates random IV for AES-GCM
3. A encrypts message content with conversation key + IV
4. A signs encrypted message with private signature key
5. A stores encrypted message, IV, signature, and content hash
6. B receives notification of new message
```

### 3. **Message Decryption**
```
User B reads message from User A:
1. B retrieves encrypted message from database
2. B decrypts conversation key with private key
3. B decrypts message content with conversation key + IV
4. B verifies signature using A's public key
5. B verifies content hash matches decrypted content
6. B marks message as read
```

## Security Features

### 1. **Perfect Forward Secrecy**
- **Key Rotation**: New conversation keys generated periodically
- **Ephemeral Keys**: Temporary keys for sensitive conversations
- **Key Compromise**: Compromised keys only affect current conversation

### 2. **Message Authentication**
- **Digital Signatures**: Ed25519 signatures verify sender identity
- **Content Integrity**: SHA-256 hashes prevent message tampering
- **Replay Protection**: IVs ensure unique encryption for each message

### 3. **Key Verification**
- **Fingerprint Comparison**: Users can verify keys match expected values
- **Out-of-Band Verification**: Manual verification for high-security conversations
- **Trust on First Use**: Automatic key acceptance for convenience

### 4. **Privacy Protection**
- **Zero-Knowledge Server**: Server cannot read message contents
- **Metadata Minimization**: Minimal conversation metadata stored
- **User Control**: Users control their own encryption keys

```yaml
          backoffLimit: 3
```

#### Key Rotation Logic
The rotation job performs the following operations:

1. **Identify Rotatable Keys**
   - Conversation keys older than 30 days
   - Message encryption keys older than 7 days
   - Signature keys older than 90 days

2. **Generate New Keys**
   - Create new keys for each expired key
   - Encrypt new keys with current role keys
   - Store new keys in database

3. **Cleanup Old Keys**
   - Mark old keys as expired
   - Schedule old keys for deletion after grace period
   - Maintain audit trail of key rotations

4. **Batch Processing**
   - Process keys in configurable batches
   - Use database transactions for consistency
   - Log rotation progress and failures

The existing `generate-ibe-keys` command will be modified to preserve existing keys:

```go
// cmd/server/commands/ibe_keys.go
func initializeIBESystem(opts *IBEKeyOptions) (*ibe.IBESystem, error) {
    domainMasters := make(map[string][]byte)
    
    // Define all domains that need keys
    domains := []string{
        ibe.DOMAIN_USER_PSEUDONYMS,
        ibe.DOMAIN_USER_CORRELATION,
        ibe.DOMAIN_USER_MESSAGING,  // NEW DOMAIN
        ibe.DOMAIN_MOD_CORRELATION,
        ibe.DOMAIN_ADMIN_CORRELATION,
        ibe.DOMAIN_LEGAL_CORRELATION,
    }
    
    // Load existing keys first
    for _, domain := range domains {
        keyPath := filepath.Join(opts.OutputDir, "domains", domain+".key")
        if existingKey, err := os.ReadFile(keyPath); err == nil {
            // Key exists - preserve it
            domainMasters[domain] = existingKey
            log.Info().Str("domain", domain).Msg("Preserving existing domain key")
        } else {
            // Key doesn't exist - will generate new one
            log.Info().Str("domain", domain).Msg("Will generate new domain key")
        }
    }
    
    // Generate only missing keys
    for _, domain := range domains {
        if _, exists := domainMasters[domain]; !exists {
            newKey := make([]byte, 32)
            if _, err := rand.Read(newKey); err != nil {
                return nil, fmt.Errorf("failed to generate key for domain %s: %w", domain, err)
            }
            domainMasters[domain] = newKey
            log.Info().Str("domain", domain).Msg("Generated new domain key")
        }
    }
    
    return ibe.NewIBESystemWithOptions(domainMasters)
}
```

## Key Management Strategy

### Server-Side Key Storage
- **Advantages**: 
  - Users don't lose access if they forget passwords
  - Keys can be rotated automatically
  - Server can enforce key policies
- **Disadvantages**: 
  - Server has access to encrypted keys
  - Requires trust in server security

### Password-Based Encryption
- **Implementation**: PBKDF2 with high iteration count
- **Security**: Keys protected by user's password strength
- **Recovery**: Keys recoverable with correct password

### Key Rotation
- **Automatic**: Every 100 messages or 30 days
- **Manual**: User-initiated key rotation
- **Emergency**: Immediate rotation on compromise detection
